核心定义

Team = 一个 leader + 一群有角色的成员

members

一组 Agent，甚至子 Team（可以嵌套）
官方建议给成员设稳定 id：成员选择和运行追踪都靠它

leader

读每个成员的 role，决定把任务派给谁
role 写得越具体、越不重叠，派得越准

model 继承

成员没配 model 时，自动用 Team 的 model
个别成员可用别的模型单配

你把「分工表」写好，调度交给 leader。

运行机理 · 来自 01_basic_team.py 的事件流

委派是怎么发生的

① 分析

leader 读输入，决定找谁

→

② 派活

调用工具 delegate_task_to_member
参数：member_id + task

→

③ 执行

成员各自干活
异步时多个成员并发

→

④ 综合

leader 汇总成最终回答

事件流里能清楚看到 leader 的每次 delegate_task_to_member 调用 —— 调试就看它。

四种协作模式 · 显式 mode= TeamMode.xxx

一张模式地图，先存脑子

coordinate

默认。leader 选成员、拆任务、综合结果
你的 01/02/05/06/07 都是它

route

只选一个成员，结果直接返回，不综合
03_math.py；成本最低

broadcast

同一任务发给全部成员，再综合
04_collaborate.py

tasks

leader 建共享任务列表，迭代执行
max_iterations 限循环；本仓库暂无示例

⚠ 没有 collaborate 这个模式名 —— 你的目录为此踩过坑：多源同题研究叫 broadcast。

模式特写 ① · examples/05_teams/03_math.py

route：分诊台，只管转不管治

math_team = Team(
    id="math_route_team",
    mode=TeamMode.route,
    members=[addition_agent,
               subtraction_agent,
               multiplication_agent],
    instructions=[
        "分析问题类型（加法/减法/乘法）",
        "将任务路由给最匹配的一位专家",
    ],
)

为什么便宜

leader 只做分类分发，没有综合步骤 —— 延迟和 token 都省。

⚠ 你踩过的坑

曾让 route 处理「先加再乘」—— 它只选一个成员！输入必须只含单一运算。

模式特写 ② · examples/05_teams/04_collaborate.py

broadcast：同一道题，全员开考

    mode=TeamMode.broadcast,
    members=[reddit_agent,
               news_agent,
               academic_agent],
    instructions=[
        "将同一研究任务广播给所有成员",
        "识别共识与分歧",
        "生成全面的研究报告",
    ],
# 要成员并发：await team.aprint_response(...)

适合场景

多源对照：社区观点 vs 媒体报道 vs 学术研究，leader 只做综合。

并发条件

成员要真正同时跑，得用 arun() / aprint_response()。

模式特写 ③ · examples/05_teams/01_basic_team.py

coordinate：instructions 是写给 leader 的

    mode=TeamMode.coordinate,
    instructions=[
        "必须先委派 Web Agent 搜索最新资料，不能跳过。",
        "必须再把结果交给 Research Agent 分析。",
        "最后汇总团队结论并保留来源链接。",
    ],
    stream=True, stream_events=True,
    stream_member_events=True,

约束委派顺序

「必须先…再…」写给 leader 看，规范它的派活路径。

流式三件套

stream 只流正文；stream_events 才有工具/错误事件；stream_member_events 让成员事件冒泡上来。

版本陷阱 · 你的 05_coordinate.py 踩过

旧布尔开关 → 新模式对照表

respond_directly=True

→ 等效 route

delegate_to_all_members=True

→ 等效 broadcast
两个开关同设时 broadcast 胜出

两个都 False

→ 等效 coordinate

✍ 记住这一条

显式写 mode=TeamMode.xxx 会覆盖旧开关。你曾经在 coordinate 里设 delegate_to_all_members=True，结果实际跑成了 broadcast —— 新模式写明白，旧开关别碰。

账本时间

Team 的第一性问题：贵

“A 4-member team can easily use 10x the tokens of a single agent.” — docs.agno.com/teams/debugging-teams

coordinate

成本 高
分解 + 综合两头花

route

成本 低
只做选择

broadcast

成本 中
只综合一次

tasks

成本 高
规划 + 迭代循环

降本三招：减成员 · 让成员回答简短 · 能用 route 别 coordinate

可调试性

成员会静默失败 —— leader 照样综合

👀 看见成员

show_member_responses=True（print_response 里是单数 member）或读 TeamRunOutput.member_responses

🔍 开调试

debug_mode=True，debug_level=2 更细；环境变量 AGNO_DEBUG=True 也行

🔁 防死循环

委派停不下来？instructions 写死停止条件：
"Do not delegate more than 3 times per request"

生产环境靠 AgentOS tracing，不靠终端肉眼。

排障决策

成员输出差，改哪一层？

选错成员

→ 改 role
让角色具体、互不重叠 —— role 重叠是派错人的头号原因

干得不完整

→ 改成员的 instructions
任务要求、输出格式、边界写清楚

拿不到数据

→ 改 工具配置
如 YFinance 的 enable_* 显式开关没开

只调用了一个成员？先查是不是 route 模式，再查 role 是否清晰、成员是否提前失败。

划清边界

Team ≠ Workflow

Team：动态分工

步骤顺序由 leader 模型现场决定 —— instructions 能引导，但不保证确定性。适合开放式协作。

Workflow：固化流程

业务上必须保证「采集 → 清洗 → 分析」这个顺序？那应该写 Workflow 的步骤流水线（ch6 的主角）。

要灵活找 Team，要确定找 Workflow。

自测 · 合上书能答几条？

检查点四连问

  • 这个任务真的需要 Team 吗？判断信号是什么？提示：多领域/多工具/上下文；否则先单 Agent
  • 四种模式各一句话：coordinate / route / broadcast / tasks？提示：分解综合 / 选一个直返 / 全员同题 / 任务列表迭代
  • 成员输出质量差，role、instructions、工具分别对应哪种病根？提示：选错人 / 干不好 / 没数据
  • 降 token 的三招是什么？提示：减成员、回答简短、用 route
